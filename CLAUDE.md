## Project

HouseDataBrowser is a Dutch-language web app that lets the user (Erik) explore his
home InfluxDB 1.x sensor data — temperature, humidity, doors, electricity, weather
— through natural-language chat. The agent translates questions into InfluxQL,
runs them, and renders charts/tables/summaries. Pinned charts go on a draggable
dashboard. UI strings and LLM responses are in **Dutch**; code, comments, log
messages, and commit messages stay in **English**.

The data labels in InfluxDB are mostly Dutch with some English mixed in (e.g.
`temperatuur`, `kamer`, `voordeur`). The agent quotes identifiers verbatim.

## Architecture invariants — what's load-bearing across files

### 1. The InfluxQL safety filter is THE security boundary

Every query — whether generated by the LLM, written by the user, or hardcoded
in `schema_discovery.py` — passes through `backend/app/influx/safety.py` before
reaching InfluxDB. It's a token-level whitelist: only `SELECT` / `SHOW` /
`EXPLAIN` allowed, multi-statement rejected, deny-list keywords blocked
anywhere in the token stream, and a `LIMIT` is auto-injected on `SELECT`. The
28 tests in `tests/test_safety.py` cover injection attempts; they MUST stay
green for any code change touching query handling. **Never bypass `validate()`
for "internal" queries** — the tests assume it's the only path.

### 2. LLM provider abstraction is intentionally thin

`backend/app/llm/provider.py` defines a `Protocol` with one async `chat(...)`
method, plus an optional episode capability (`runs_own_loop` +
`run_episode(...)`) for engines that drive their own agent loop.
`ClaudeCodeProvider` (Claude Code via the Agent SDK, subscription auth) uses
the episode path; `OllamaProvider` uses per-turn `chat()`. The
`ProviderRegistry` (`backend/app/llm/registry.py`) holds both at runtime —
`claude` and `ollama` load independently and a missing
`CLAUDE_CODE_OAUTH_TOKEN` or unreachable Ollama just marks that provider
unavailable, never crashes the app.

The chat endpoint resolves per-request via `body.provider`. **Agent code
(`app/agent/`) never imports either implementation directly** — only the
`Protocol` and the registry. Adding a third provider should require zero
changes outside `app/llm/` and the model lists in `registry.CLAUDE_MODELS` /
the Ollama tag probe.

Provider-specific features live entirely in `claude_code.py`. The Claude
model list uses subscription aliases (`opus`/`sonnet`/`haiku`) that track the
subscription's current models, so no stale IDs. Ollama silently ignores
`effort`/`model` overrides it doesn't understand.

### 3. The agent loop has two paths: classic per-turn and episode delegation

`backend/app/agent/loop.py` is the heart. Three tools defined in `tools.py`:
- `get_schema_for(measurements)` — fetches tag/field details on demand
- `run_influxql(query)` — runs through the safety filter, returns preview + `data_ref`
- `render_response(summary, query, chart, data_ref)` — **terminal**, ends the turn

The loop yields SSE events (`agent_start`, `assistant_text`, `tool_call`,
`tool_result`, `usage`, `final`, `done`, `error`). It exits on
`render_response`, on `end_turn` with no tool calls, or when `max_agent_steps`
is hit (configurable via `LLM_MAX_AGENT_STEPS`, default 12).

For a `runs_own_loop` provider (Claude Code) the loop delegates the whole
episode to `provider.run_episode(...)`: the SDK drives the agent loop as a
subprocess, HDB's tools are in-process MCP tools, and **tool execution still
happens in loop.py's handler callback** — the safety filter and terminal-tool
bookkeeping are identical on both paths. Episode events are translated to the
same SSE events, so `chat.py` persistence works unchanged.

Two non-obvious quirks:

- Claude Code built-in tools (Bash/Read/Write/...) are disabled via
  `tools=[]` + `allowed_tools=[mcp__hdb__*]` + `permission_mode="dontAsk"` in
  `claude_code.py`. Don't loosen this — the InfluxQL safety filter is the
  security boundary and the only tools the model may touch are HDB's three.

- The agent's `final` event is emitted whether or not `render_response` was
  called. If Claude finishes without it, `_fallback_message(stop_reason)`
  produces a Dutch error explaining the cause (`max_tokens` / `refusal` / etc.)
  rather than a confusing `(no response)`.

### 4. Conversation history is collapsed, not replayed

`backend/app/api/chat.py:_load_history` rebuilds each prior assistant turn from
its `final_summary` + `final_query`, **not** from the raw `tool_use` blocks
stored on the message. This is essential: replaying `tool_use` without the
matching `tool_result` blocks (which we never persist as messages) would 400
the Anthropic API with `tool_use ids were found without tool_result blocks`.

The query is included so follow-ups like "doe nu hetzelfde voor 2024" have
the working query as context. **Don't try to "fix" this by persisting tool
results as messages** — that path was tried and bloats history without
helping coherence.

### 5. Schema RAG is prompt-cached, not embedded

The user has 562+ measurements. We don't use `sentence-transformers` or any
vector store. Instead, `backend/app/agent/system_prompt.py` injects a
deterministic list of all measurement names + their human descriptions
(~15K tokens) into the system prompt. Anthropic's prompt cache then makes
this prefix nearly free on subsequent turns (~0.1× cost). Tag/field details
load on demand via `get_schema_for`.

If you ever consider adding embeddings: don't. The cache approach is faster,
cheaper for our scale, and avoids a multi-GB PyTorch dependency. The
deterministic ordering (sorted by measurement name) is critical for cache
hits — never sort by anything that changes per request.

### 6. SQLite concurrency: WAL + per-measurement commits

`backend/app/state/db.py` enables WAL mode + 30s busy_timeout on engine
creation. `schema_discovery.discover()` commits after **every measurement**,
not at the end. Both are required: a single 30+ second discovery transaction
blocked the chat endpoint with `database is locked`. Keep both.

### 7. Pinned charts re-run their query on load

`backend/app/api/pins.py` stores InfluxQL + chart spec only — no data. Each
tile in `frontend/src/pages/Dashboard.tsx` fetches `/api/pins/{id}/data` on
mount, which re-runs the query through the safety filter. A pinned
"temperatuur vandaag" stays current; storage is small and time-aware.

### 8. SSE uses POST, not GET

`@microsoft/fetch-event-source` is used because native `EventSource` only
supports GET, and chat messages need a POST body. The events are JSON-encoded
in `data:` lines; the agent loop yields dicts and the API layer wraps with
`sse-starlette`'s `EventSourceResponse`.

## Project conventions

- **Dutch in the UI, English in the code.** All user-facing strings (chat
  thread, sidebar, schema page, dashboard, errors) are Dutch. Code, comments,
  log messages, error messages thrown in code, file/branch names, and commit
  messages stay English. The agent's system prompt is English (Claude
  understands both); only the *example* output strings in the prompt are Dutch.

- **Effort levels** are enforced by the Pydantic `Literal` type in code — that
  type is the source of truth for allowed values, not this file. Default is
  `high`; the "🧠 Diep nadenken" UI toggle bumps a single message to the
  highest allowed level. Disabled when Ollama is the active provider.

- **The default Claude model lives in config** (`.env` /
  `registry.CLAUDE_MODELS`), not in this file — model names go stale. Don't
  change or downgrade the configured default except on explicit request.

- **Persist user feedback to memory** when learning a new preference. The
  memory store at `/Users/erik/.claude/projects/-Users-erik-GenAI-HouseDataBrowser/memory/`
  has project + feedback memory files; check `MEMORY.md` for the index
  before assuming defaults.

## When extending the agent

The most likely productive changes:

- **New tool**: add to `app/agent/tools.py`, register in `ALL_TOOLS`. Tool
  results round-trip as JSON strings (Anthropic's tool_result content is a
  string), so dict results go through `json.dumps`. Don't mark a tool as
  `terminal` unless it ends the turn — only `render_response` does.

- **Prompt-cache hits**: keep the system prompt's render order
  (header → schema overview → footer) deterministic. Anything that changes
  between calls (timestamps, per-user data, different tool sets) breaks the
  cache for everything after it. Verify with `response.usage.cache_read_input_tokens`.

- **New provider**: implement `LLMProvider`, register in `ProviderRegistry`,
  add to the `make_provider` factory + the registry's `CLAUDE_MODELS`-style
  list (or live-probe pattern). The frontend `ProviderPicker` will pick it
  up automatically from `/api/providers`.

## What's deliberately not done

- No vector embeddings / sentence-transformers (see §5 above).
- No streaming of LLM tokens to the UI — the SSE layer streams agent-loop
  events (per-tool-call), which gives a much clearer progress UX than per-token.
- No multi-database support (single InfluxDB target).
- No auth — single user on a trusted home network.
- No automated full-stack integration tests (the safety filter has thorough
  unit coverage; agent loop has mocked-LLM smoke tests run ad-hoc).
